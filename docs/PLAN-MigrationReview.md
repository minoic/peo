# server 后端架构、具体实现与代码规范审查计划

## 1. 目标与边界

对 `server/` 全部手写后端源码及已有测试进行静态审查，交付**架构与实现说明、证据化问题清单、分阶段整改路线**，本阶段不修复代码。

- 基线采用审查开始时的当前工作区，包含未提交修改和未跟踪源码；记录 Git 状态，避免与历史版本混淆。
- 关联阅读项目开发约定、API／路由／数据契约、CI 和部署配置；Flutter 与 Panel 代码仅在核对接口边界时定向查阅。
- 不运行构建、测试、静态分析工具或外部服务；不修改源码、配置、测试及现有文档。排除调试二进制、生成资源和第三方代码。
- 以当前实现和明确的项目约定为依据；文档与实现不一致时记录差异，不自行决定业务语义。

## 2. 审查步骤与覆盖内容

### 第一阶段：建立架构与覆盖清单

枚举所有后端包、源码文件、路由及测试，建立覆盖矩阵，绘制包依赖关系和主要请求链路。

对每个模块说明：职责、入口、关键类型与函数、调用关系、数据读写、共享状态、错误处理、现有测试及维护风险。每个源码文件必须有审查状态，避免只检查核心模块。

### 第二阶段：逐层检查具体实现

| 模块 | 核心审查内容 |
|---|---|
| 入口与生命周期 | 初始化顺序、配置加载与首次写入、启动失败清理、HTTP 超时、信号处理、后台任务停止与资源释放 |
| API、DTO、错误封装 | 路由与权限分组、参数及 ObjectID 校验、响应一致性、业务逻辑是否越层、下载／回调／流式响应的特殊处理 |
| 身份认证与中间件 | JWT 签发解析、注销黑名单、用户权限重新读取、可选认证、限流、CORS、日志与 panic 恢复 |
| 业务服务 | 商品、订单、余额与密钥支付、充值回调、续费、实例生命周期、消息、工单、展示及管理员操作的完整调用链 |
| 数据模型与存储 | BSON／JSON 字段、时间戳、查询与更新条件、分页排序、索引、唯一性、原子操作、并发写入及错误语义 |
| 配置、Redis 与缓存 | 配置校验及保存生效、依赖客户端重建、键名与 TTL、共享状态锁、失效机制及多实例限制 |
| 定时任务 | 调度与实际任务生命周期、任务重叠、context 传播、超时、取消、异常恢复与退出等待 |
| 外部服务与控制台 | Panel 扩展协议、HTTP 超时与响应关闭、凭据边界、文件传输、终端票据与 WebSocket 生命周期、SMTP 和 Alipay 失败处理 |
| 辅助包及部署边界 | 加密与随机数、状态探测、构建信息、SPA 静态资源、工具链与 CI／Docker 配置一致性 |

跨层重点追踪以下场景：重复支付与回调、余额并发扣减、外部开服成功但本地写入失败、续费与过期任务交错、配置更新与在途请求交错、注销与活动终端会话交错。检查幂等、补偿和状态恢复是否形成闭环。

### 第三阶段：规范性与可维护性检查

- 检查依赖方向、职责划分、重复实现、过大函数、全局单例与可测试性；不以引入接口或设计模式的数量评价架构。
- 检查命名、包组织、导出注释、错误包装与判定、context 使用、资源关闭、锁作用域及 goroutine 生命周期。
- 检查日志是否支持定位问题，是否泄露敏感数据，以及注释是否准确描述实现。
- 核对分层约束测试的实际覆盖能力，识别字符串匹配、仅检查 import 等方式可能遗漏的情况。
- 区分项目约定违规、可证实缺陷和可选风格建议，避免将个人偏好列为必须整改项。

## 3. 测试与证据审查

只阅读已有测试及 CI 定义，不执行检查；既有测试存在不等于当前通过。

建立“行为—实现—测试—缺口”矩阵，至少覆盖：

- 身份边界：匿名、过期或注销令牌、权限变更、跨用户资源访问。
- 资金与订单：重复请求、并发扣款、重复回调、失败补偿及重试。
- 生命周期：开服、续费、重装、删除、过期处理与定时任务竞争。
- 控制台：票据过期或重用、Origin 校验、注销断连、上下游断开和文件传输失败。
- 基础设施：数据库／Redis／Panel 不可用、超时、配置刷新、缓存并发和关闭流程。

每条发现必须提供文件与行号、调用链或数据流依据、触发条件、影响、建议和验收方法。证据状态分为“静态可确认”“待运行验证”“设计建议”；没有运行证据时不宣称已复现。

## 4. 交付物与验收标准

交付一份中文审查报告，包含：

1. **架构与实现说明**：模块职责、依赖图、关键业务时序及现有设计取舍。
2. **问题清单**：按严重程度排序；严重程度依据数据／资金／权限／可用性影响，证据置信度单独标注。
3. **规范与契约差异**：代码约定违规、文档漂移、测试及 CI 保障缺口。
4. **整改路线**：优先处理正确性与权限边界，其次处理并发、生命周期和数据一致性，最后处理可维护性与风格；每项明确修改范围、依赖、兼容影响和回归验收条件。

验收要求：全部手写源码有覆盖记录；全部业务域有实现说明；每条问题有可定位证据；所有未验证行为明确标注；不得因缺少运行验证推断系统整体可靠。

本次不新增或修改公共 API、数据类型、数据库结构，不用与 legacy 实现做对照。发现需要调整时，仅在整改建议中写明兼容与迁移要求。审查由主代理分块分配给 `development_assistant` 完成；后续进入实现阶段时，按项目约定将修改及相关测试委派给 `development_assistant`，由主代理审查和汇总验证结果。
